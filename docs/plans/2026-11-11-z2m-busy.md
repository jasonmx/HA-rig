# Z2M coordinator BUSY: rig resend, rerun, pacing, log capture

Agreed with Jason 2026-11-11. All four parts land before the house rerun of the Z2M group cases.

## Coordination

Intent: keep a Z2M coordinator refusing groupcasts with BUSY from failing rig cases, pace Z2M group cases so it
happens less, and fix the two rig bugs that kept `group_color` from running in the house run.
Touches: ha_rig/engine.py, ha_rig/roam.py, ha_rig/runlogs.py, ha_rig/client.py, tests/**

## Why

House run `rig-run-2026-11-11-155622`: two Z2M group cases failed because the coordinator answered `BUSY` to the
groupcasts (Z2M log 15:57:32.184/.193, 15:58:27.330/.415). Herdsman's Ember adapter retries BUSY on unicasts but not
on group sends. In `sets_after_a_soft_off[group]` only the rig's own `set`s were dropped (in `steps:`, which #57's
setup-only retry doesn't cover); in `lower_to_a_limit[group]` DeviceSide's call was dropped too. `group_color` never
ran: its group stayed unavailable 60 s. The full diagnosis is in deviceside's gitignored
`notes/rig-runs/2026-11-11-house-z2m-busy-diag.md` (ask Jason for it if this checkout can't reach it).

The paired deviceside change (`notes/plans/2026-11-11-z2m-set-failed.md` there) makes DeviceSide answer
`targets_failed` with Z2M's message when Z2M logs a set it sent as failed. The rig parts below key on the Z2M log,
so they work with or without it.

## Parts

**(a) Resend a rig `set` on BUSY.** When Z2M logs `Publish 'set' ... to '<target>' failed: ... status=BUSY` for a
rig `set` (setup or steps; the target or the group it belongs to), send it once more, traced once in the report
(one line naming the case and the step). A second BUSY fails the step as today. Distinct from #57's setup retry,
which is for a stale member report; keep both, and pin that a step `set` resends only on BUSY (#57's
`test_a_set_in_steps_is_not_retried` stays true for the no-BUSY case).

**(b) DeviceSide's call hit BUSY: rerun, never fail.** A BUSY line for the case's target within the call's window
(the call's start to its answer + 1 s) means the case didn't test DeviceSide. Restore, wait ~10 s, rerun the case
once. A second BUSY reports the case `not run: coordinator busy`, never `fail`, and it is not saved as passed (resume
runs it again; the record lacks it until it passes).

**(c) Pace Z2M group cases.** Wait `RESTORE_SETTLE_S` (1.5 s) after each Z2M group case's restore even when nothing
was put back (today the sleep runs only `if clear and put_back`), so the next case's groupcasts don't land in the
previous case's broadcast-table entries (~9 s each on EmberZNet). Z2M group cases only; don't slow other suites.

**(d) Log capture and group availability.**
- The Z2M log capture went silent after 16:01:48.114 while the run went on to ~16:03:17. Find why (subscription
  dropped across a Z2M restart or network close? log level changed by a step?), fix, and pin it with a test.
- Before making a Z2M group, wait until each member's Z2M availability is `online`; `roam.py` `live()` counts "no
  sign either way" as live, which is right for locating but not for this. Then wait for the group's own
  availability topic to say `online` before the case starts, bounded, with a clear setup failure naming the member.
